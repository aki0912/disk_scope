# 性能改善の測定

2026-09-27、macOS 27 / Apple Silicon、Swift 6.4、Rust 1.98.1のリリースビルドで測定。比較元は初回コミット `58f1242`。

| 処理・条件 | 改善前 | 改善後 | 短縮率 |
| --- | ---: | ---: | ---: |
| 1フォルダに5万ファイル：走査からJSON出力まで | 173.05 ms | 60.60 ms | 約65% |
| 200フォルダに合計5万ファイル：走査からJSON出力まで | 74.25 ms | 71.81 ms | 約3% |
| 5万項目から画面用の上位300件を選出 | 248.22 ms | 15.13 ms | 約94% |

走査の比較は同じ空ファイル群を使用し、変更前後を交互に実行。各バイナリの初回を除外し、続く8回の中央値を使用した。OSのキャッシュが温まった条件であり、初回読み込みや外部SSDの結果は異なる。分散したフォルダの差は小さく、明確な高速化とは判断していない。

走査時間にはプロセス起動、完了通知のポーリング、JSON生成、標準出力への転送を含む。Python側のJSON解析時間は含まない。Swiftの選出処理は、同じ容量の5万項目を使用し、元の全件ソートと上位選出の結果が一致することを毎回確認した。こちらも初回を除く8回の中央値。SwiftのJSONデコード、描画、アプリの起動時間はこの選出時間に含まない。

## 変更内容

- 大きいフォルダのメタデータ取得を512件ずつに分け、最大8ワーカーに分配。小さいフォルダは担当ワーカー内で処理し、キューの負荷を抑える。
- 完了結果のキューを16バッチに制限。キャンセル時に受信側を閉じ、送信待ちのワーカーが終了できるようにする。
- 進捗の共有カウンターをファイルごとではなくバッチ単位で更新する。
- 全件の並べ替えを廃止し、一覧は上位300件、ツリーマップの内部は上位45件だけをヒープで選出する。選出中に全項目の件数・容量を集計し、「その他」の面積を維持する。
- 名前検索も全項目を対象に上位を選出し、画面の再描画時に同じ検索を繰り返さない。

## スキャン開始から初回の地図描画まで

2026-09-27、同じMacのリリースビルドで比較。比較元は描画修正後の `c955a47`。1ファイル1バイト、1千・1万・5万件を使用。階層ありの条件は10グループの下に計100フォルダへ分散した。

実際の `ContentView` を1440×940の検証ウィンドウに表示し、マウス入力を無効にした。計測範囲は `ScannerModel.start` の呼び出しから、空ではない最初のCanvas描画コールバックの終了まで。アプリ起動時間、フォルダ選択ダイアログ、GPU描画・画面への提示完了は含まない。

初回を別集計し、その後の8回を変更前後で交互に実行。以下のP95は8標本のnearest-rank値で、この標本数では最大値に一致する。ファイル作成直後はOSのキャッシュに載るため、初回欄もコールドキャッシュの測定ではない。外部SSDやOSキャッシュを空にした条件への一般化はしていない。正式測定中は他の検証を同時実行していない。

### 変更内容と検証

- C ABIに `ds_scan_wait(id, timeout_ms)` を追加。戻り値は `-1` が未登録、`0` がタイムアウト、`1` が完了、`2` がキャンセル、`3` が失敗。結果は消費せず、既存の取得APIとJSON形式を維持する。
- Rustの条件変数を使い、完了・失敗・キャンセル・破棄で待機を解除する。SwiftはDispatchのバックグラウンドワーカーで待ち、進捗表示は従来どおり約120 ms間隔で取得する。
- 結果の読み込みと初回上位選出を同じバックグラウンド処理で行い、準備済みデータを反映する。途中でキャンセルされた結果は世代番号で破棄する。
- JSONの文字列エスケープと親IDを出力バッファに直接書き込み、バッファを事前確保する。
- Rust 13テスト、Swift 5テスト、13,304ファイルの容量照合、10項目の描画・キャンセル検証が通過。1万ファイルの単一・分散フォルダでは、旧版と項目ごとの名前・種別・容量・日時・状態、集計件数も一致した。

生の各回の結果は [FIRST_FRAME_RESULTS.json](FIRST_FRAME_RESULTS.json) に保存している。

## 検索の応答とJSON受け渡しのメモリ削減

2026-09-27、同じMacのリリースビルドで `4217d59` と比較。優先度の高かった検索処理の非同期化と、RustからSwiftへのJSONコピー削減を採用した。容量の計算、検索対象、並び順、最大300件の表示、C ABIは維持している。

### 検索入力

実際の `ScannerModel` に1万・5万件の合成データを渡し、検索語を設定するMainActor上の処理時間と、結果反映までの時間を測定。画面描画時間は含まない。各条件の初回を別集計し、変更前後を交互に8回実行した。各標本は新しいプロセスで取得し、結果のID・件数・容量・非ゼロ件数が同期検索と一致することも確認した。

| 件数・検索条件 | 入力受付・改善前中央値 | 改善後中央値 | 改善前の最大値 | 改善後の最大値 | 改善後の結果反映・中央値 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 10,000件・全件一致 | 10.95 ms | 0.017 ms | 11.31 ms | 0.023 ms | 138.5 ms |
| 10,000件・1件一致 | 8.22 ms | 0.019 ms | 8.44 ms | 0.028 ms | 140.6 ms |
| 10,000件・一致なし | 8.22 ms | 0.021 ms | 8.70 ms | 0.056 ms | 139.9 ms |
| 50,000件・全件一致 | 49.62 ms | 0.024 ms | 50.77 ms | 0.036 ms | 183.9 ms |
| 50,000件・5件一致 | 40.25 ms | 0.021 ms | 41.16 ms | 0.033 ms | 174.6 ms |
| 50,000件・一致なし | 40.80 ms | 0.024 ms | 41.73 ms | 0.029 ms | 174.7 ms |

全件一致は `file-0`、少数一致は `9999`、一致なしは `no-match`。連続入力中の不要な検索を減らすため120 msの待ち時間を設けた。結果反映までの時間にはこの待ち時間、バックグラウンド検索、MainActorへの復帰、検出用ポーリング（要求間隔1 ms）が含まれる。改善前は同期処理のため入力受付と結果反映の時間がほぼ同じだった。**検索結果そのものが早く出るという測定結果ではなく、入力時にメインスレッドを占有する時間を減らした改善である。** 検索中は一覧に「検索中…」を表示する。

古い検索はキャンセルし、256件ごとと結果確定前にキャンセルを確認する。検索語の変更、検索解除、容量基準変更、フォルダ移動、再スキャンで世代を更新し、遅れて届いた結果を反映しない。検索タスクからモデルは弱参照する。

### JSONのコピー削減

Rustが確保したJSONを `Data(bytesNoCopy:deallocator:)` に渡し、Dataの解放時にRustの `ds_string_free` で解放する。デコード成功・失敗のどちらでも所有権を一度だけ返す。進捗用の小さいJSONの処理は変更していない。

実際の画面の初回Canvas描画までを従来の測定スクリプトで比較した。1ファイル1バイト、単一フォルダと10グループ・100フォルダの階層を使用。初回は別集計し、続く8回を交互に実行。OSのキャッシュが温まった条件で、他の検証やベンチマークは同時に動かしていない。

| 条件 | ピークRSS最大・改善前 | 改善後 | 初回描画・中央値（前 → 後） | 初回描画・P95（前 → 後） | Swift読み込み・中央値（前 → 後） |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1,000件・単一 | 92.38 MiB | 92.42 MiB | 91.50 → 92.14 ms | 99.04 → 104.17 ms | 3.13 → 3.19 ms |
| 1,000件・階層あり | 91.80 MiB | 91.53 MiB | 86.74 → 90.75 ms | 98.72 → 100.21 ms | 3.70 → 3.39 ms |
| 10,000件・単一 | 107.09 MiB | 105.84 MiB | 109.54 → 112.71 ms | 115.73 → 117.70 ms | 27.53 → 26.33 ms |
| 10,000件・階層あり | 105.58 MiB | 104.73 MiB | 107.52 → 105.88 ms | 117.63 → 109.58 ms | 28.40 → 26.80 ms |
| 50,000件・単一 | 138.95 MiB | 132.08 MiB | 220.08 → 217.10 ms | 238.19 → 220.66 ms | 104.65 → 103.49 ms |
| 50,000件・階層あり | 162.52 MiB | 153.97 MiB | 206.38 → 204.78 ms | 211.48 → 214.86 ms | 105.59 → 105.09 ms |

5万件のピークRSS最大値は約6.9〜8.5 MiB減少。同じ条件のピークRSSの中央値も137.70 → 129.98 MiB、161.15 → 153.17 MiBに減っており、メモリ削減を採用理由とした。初回描画と読み込みの時間差は小さく、初回表示の高速化とは判断していない。RSSはアプリ起動を含む初回描画時点までのピークで、長時間の繰り返しスキャンにおけるメモリ増加を測った値ではない。8標本のP95は最大値に一致する。
